# LEVEL_DESIGN.md — 关卡设计规范

> 本文件是 ninja-run 的**关卡设计细则**，承载「Introduce → Repeat → Vary → Escalate → Recovery」
> 的完整展开、硬指标与判断依据。
>
> 长期稳定的工作规则与流程在
> `.codebuddy/skills/ninja-run-level-design/SKILL.md`；
> 当前代码架构快照在 `docs/ARCHITECTURE.md`。
>
> 本文件描述**应该怎么设计**，不描述**代码现在长什么样**。

---

## 0. 核心原则

> **关卡多样性来源于"重复中的变化"，而不是每次都换一种新障碍。**

一个 Section 应围绕**少数几个核心 Pattern** 建立，而不是不断堆叠全新机制。

玩家需要的是"我认识这个，但它变了"，而不是"每 5 秒学一个新东西"。

典型结构：

```text
P04（单飞镖）
→ P04 Variation（同一件事，只改高度）
→ P14（飞镖墙）
→ Recovery
→ P14 Variation（同一堵墙，只改缺口高度）
→ P17（缺口换位）
→ P17 Variation（只改换位间隔）
```

对应的玩家体验：

```text
学习 → 熟悉 → 变化 → 强化 → 喘息
```

### 0.1 「一次操作解决多拍」——动作句

> **同一个 Phrase 内，连续几个障碍应当共同组成一次操作过程，
> 而不是依次展示多个独立题目。**

反面写法：每个障碍各占一个 Pattern，中间自然留下大段空白。
玩家感受是「跑 → 一个障碍 → 跑很久 → 一个障碍」，
像是在**参观障碍模板**，而不是在玩一段连续的关卡。
（`Dart_Introduction` 重做前有 5680 px = 14.2 s 的纯跑动空白，
占全段的 40%。）

正面写法：用 **P30 飞镖动作句** 在**同一个 Pattern 内**编排多枚飞镖，
让第二枚出现时玩家仍在处理第一枚引发的结果：

```text
看到低位飞镖 → 起跳 → 空中经过第二个威胁 → 落地读取飞镖墙缺口
→ 选择路径 → 安全落地
```

玩家感受是「我完成了一个连续的小场面」。

**可验证判据**：相邻障碍的**相遇时刻**间隔应落在一个单跳周期
（`PlayerMotionProfile.jump_time() = 0.699 s`）的 1.5 倍以内。
超过就退化成两道独立题目。由
`tests/godot/dart_section_design_check.gd` 的「连续动作检查」程序化断言。

> **不要用留白来表达节奏。** 节奏应来自**威胁的疏密**，
> 而不是「把障碍摊开、中间塞平地」。
> `Recovery` 是唯一允许留白的地方，且应带低压力内容
> （如金币）让玩家读到「这里可以喘息」。

## 1. 五阶段模型

任何新增或调整关卡内容的方案，**必须显式标注它落在哪个阶段**，
并给出该阶段的可验证判据。

| 阶段 | 意图 | 玩家感受 |
|---|---|---|
| **Introduce** | 首次引入一个机制 | "这是什么？" |
| **Repeat** | 巩固，建立肌肉记忆 | "我会了。" |
| **Vary** | 在已学会的东西上做单一变化 | "哦，变了？" |
| **Escalate** | 组合已教机制，提升压力 | "有点忙。" |
| **Recovery** | 释放压力，回到基准 | "喘口气。" |

---

## 2. Introduce（教学）

**目标**：让玩家在**几乎不可能死亡**的条件下，认识到一个新机制的存在。

### 硬指标

| 指标 | 要求 |
|---|---|
| 机制数量 | **单一机制**，不得叠加第二种 |
| 预警 | 必须清晰可见；移动障碍必须有出生/接近预警 |
| 反应窗口 | **≥ `PatternCompiler.MIN_REACTION_TIME`**，当前硬线 **0.45s** |
| 反应窗口（正式教学） | 推荐 **≥ 0.75s** |
| 前后安全区 | **必须有**；进入前与通过后都要有安全区域 |
| 技能依赖 | **不依赖任何技能**（不用剑 / 火球 / 忍术也能过） |

### 设计要点

- 玩家应当在第一次遭遇时就明白"这里要跳 / 这里要铲 / 这里要贴绳"。
- 允许"看到就知道怎么做"，不需要试错。
- 教学段的失败惩罚应最小化。
- 参考实现：`segment_safe`（零机制热身）→ `segment_single_jump` /
  `segment_slide_intro`（单机制教学）。

---

## 3. Repeat（重复）

**目标**：把刚学会的动作固化成肌肉记忆。

### 硬指标

| 指标 | 要求 |
|---|---|
| 重复次数 | 同一核心机制出现 **2 ~ 3 次** |
| 机制内容 | **保持不变** |
| 允许变化 | 仅**轻微的位置与节奏**调整 |
| 新增修饰 | **不允许**引入 Modifier |
| 新增机制 | **不允许** |

### 设计要点

- 连续 2~3 次同机制，次数太少不形成记忆，太多会枯燥。
- 变化幅度应小到玩家不会认为"这是新东西"。
- 参考实现：`segment_double_jump`（两次落地跳）、
  `segment_triple_jump`（三次落地跳，间距 360px）。

---

## 4. Vary（变化）

**目标**：在**已经学会的 Pattern 上**改变**一个主要维度**。

### 硬指标

| 指标 | 要求 |
|---|---|
| 基础 | 必须建立在已教过的 Pattern 上 |
| 变化维度 | **恰好选一个主变化** |
| 可选维度 | `Modifier` / 高度 / 间距 / 安全口 / 密度 |
| 同时叠加新机制 | **不允许** |

### 可选变化维度

| 维度 | 说明 | 对应实现 |
|---|---|---|
| Modifier | FAST / SLOW / MIRRORED / REVERSE / DOUBLE 取其一 | `PatternModifier` |
| 高度 | 安全口或障碍的整体高度位置 | P14 / P15 / P16 的 `safe_gap_position` |
| 间距 | 障碍之间的水平距离 | `parameters` 中的 `x_spacing` 等 |
| 安全口 | 缺口大小 / 位置 | `safe_gap_size`、`gap_positions` |
| 密度 | 障碍数量 | `wall_count`、`count` |

### 设计要点

- **"Vary"不等于"换一个新 Pattern"**。它必须能被玩家认出来是同一个东西。
- 一次只动一个维度。同时动两个，玩家会当成全新机制处理，教学作废。
- 参考实现：`P14_MiddleGap` → `P15_TopGap` / `P16_BottomGap`（只改高度）；
  `P17_GapSwitch`（只改安全口位置序列）。

---

## 5. Escalate（升压）

**目标**：把**已经教学过**的机制组合起来，制造真正的压力。

### 硬指标

| 指标 | 要求 |
|---|---|
| 机制来源 | **只能组合已教过的机制** |
| 组合数量 | 允许 **2 个**已教机制叠加 |
| 压力手段 | 提升密度、速度、组合复杂度 |
| 可执行路径 | **必须存在明确可执行的通过路径** |
| 无解窗口 | **不得出现** |
| 前一阶段 | 上一步必须已完成 Repeat 或 Vary |

### 设计要点

- 玩家的失败应当归因于"我操作没跟上"，而不是"这不可能过"。
- 允许玩家用技能主导化解，但**不得把技能设为唯一解**。
- 编译器会自动检查反应时间、跳跃跨度、安全口净高、坑宽；
  这些检查通过**不等于**组合有解。
- 参考实现：`P21_SpikeShuriken`（地刺 + 飞镖）、
  `P22_GapCeiling`（坑 + 顶部飞镖）、
  `P24_WallLandingTrap`（墙 + 落点陷阱）、
  `P28_RhythmBurst`（节奏组合 + `final_pattern`）。

---

## 6. Recovery（释放）

**目标**：明显降低操作压力，让玩家重新进入基准节奏。

### 硬指标

| 指标 | 要求 |
|---|---|
| 强制障碍 | 无，或仅有零风险收集物 |
| 长度 | 根据 `PlayerMotionProfile` 确定，需覆盖**至少一个完整跳跃周期的落地缓冲** |
| 数据表达 | 优先使用 `RecoverySection`；`duration` 范围 0.5 ~ 2.0 秒 |
| 与下一段关系 | Recovery **之后**才允许开启下一个 Introduce |

### 长度建议

- `RecoverySection.distance(run_speed) = duration * run_speed`；
  基础跑速 400 px/s。
- 参考 `PlayerMotionProfile.jump_time()`（约 0.70s）与
  `RUN_SPEED * jump_time()`（约 279px 单跳跨度）作为心理基准：
  恢复段至少应长于一次完整跳跃的落地周期。
- **注意**：滑铲会加速（峰值 620 px/s），实际经过时间会缩短。
  评估恢复是否充分时应按最坏情况（最高速）复核。

- 参考实现：`segment_rest`、`segment_finish`、
  `patterns/library/Recovery.tres`。

## 7. Phrase 的定义

**Phrase = 关卡设计语义单位。**

它指的是**一串有教学意义的 Pattern 序列**，例如：

```text
场景1 认识飞镖（齐胸 + 高位，一个动作句）
→ 场景2 连续跳跃（低 + 高 + 齐胸，一个动作句）
→ 场景3 读取缺口（起跳 → 落地读飞镖墙）
```

这三组合起来构成一个 Phrase：教飞镖、变化飞镖、引入安全口。

### 7.1 命名：用玩家能理解的名字

`P04` / `P14` / `P17` 这类编号是**内部技术 ID**，不作为玩家与设计者沟通的语言。

每个 `ObstaclePatternData` / `PatternSectionData` / `RecoverySection`
都应填写 `display_name`，描述它的**真实行为**：

```text
Section: 飞镖教学
Stage:   场景1 认识飞镖
Pattern: 齐胸飞镖接高位飞镖 (P30)
```

F1 覆盖层优先显示 `display_name`，内部编号放在括号里。

人工反馈因此可以直接写成自然语言，不需要记编号：

> 「第二个飞镖墙太简单」
> 「连续跳跃那段没压力」
> 「上下换位以后留白太长」

这要求 `display_name` **描述行为**而不是描述代号 ——
「中位缺口飞镖墙」是好名字，「P14 变体 B」不是。

### 表达方式

- **优先使用现有数据结构**：`PatternSectionData.entries`
  （`Array[Resource]`，元素为 `ObstaclePatternData` 或 `RecoverySection`）。
- 如果现有结构已经能表达所需序列，**直接使用，不要新增类型**。
- 只有当实际开发中出现**现有结构确实无法表达**的需求时，
  才扩展现有 Section 数据能力。

### 与链式采样的关系

```text
Route → Segment → Section → Phrase → Pattern → Obstacle
```

Phrase 位于 Pattern 之上、Section 之下。
一个 Section 由若干 Phrase 组成；一个 Phrase 由若干 Pattern（及其 Variation）组成。

## 8. 空间推导规则

**所有跳跃/滞空相关数值必须从 `patterns/player_motion_profile.gd` 推导，
禁止在关卡数据里手写魔法数字。**

`PlayerMotionProfile` 直接 `preload("res://player.gd")`，
是运动数学的唯一入口：

| 方法 | 含义 |
|---|---|
| `jump_height()` | 单跳最高点 |
| `jump_time()` | 单跳完整滞空时间 |
| `double_jump_height()` | 峰顶二段跳理论总高度 |
| `fast_fall_time(height)` | 从指定高度快速下落所需时间 |

常量：`RUN_SPEED`、`BODY_SIZE`、`GROUND_Y = 460.0`。

### 使用惯例

- 障碍间距 → `RUN_SPEED * jump_time()` 或 `fast_fall_time()`
- 安全口净高 → `BODY_SIZE.y + 容错`
- 坑宽 → `RUN_SPEED * jump_time() - BODY_SIZE.x`
- 恢复段长度 → `RecoverySection.distance(RUN_SPEED)`

### 已知公式值（仅供参考，随时以代码为准）

- 单跳高度 ≈ 140px，滞空 ≈ 0.70s，跨度 ≈ 279px
- 峰顶二段跳理论高度 ≈ 270px
- 60Hz 实测：一段跳 ≈ 133px，二段额外升高 ≈ 124px

**公式不替代实际输入路线验证。**

## 9. 玩家正式战斗能力（用于设计压力评估）

评估"玩家能不能化解这段障碍"时，按以下能力集计算。

### 9.1 武器

当前装备表现为**剑**。

剑本身**当前不作为一个独立的普通近战技能**进入正式关卡能力设计。
（代码中仍存在剑斩相关实现，见 SKILL.md 的"正式能力与残留代码区分"规则。）

真实依据：`game.gd` 明确注释"不再连接 `sword_requested`"。

### 9.2 武器主动技能（火球）

激活武器技能后：

- 角色周围**视觉上始终维持 3 颗环绕火球**（环绕半径 62px）
- 这三颗火球围绕角色运行，**是环绕槽位 / 视觉库存的表示**
- 技能持续期间循环执行：

```text
环绕火球
→ 发射一颗攻击火球
→ 发射出去
→ 对应环绕位置立即补出新的火球
→ 继续保持三颗环绕火球
→ 再次发射
```

因此：

> **"三颗火球"描述的是环绕槽位 / 视觉库存数量，
> 不代表技能只发射三发。**

> **技能实际表现是：在持续时间内，以三颗常驻环绕火球作为视觉核心，
> 持续向目标发射并自动补充火球。**

关卡设计评估玩家攻击能力时，应把它理解为：

```text
持续型武器技能，按固定节奏「每轮一颗」持续输出
```

而**不是**：

```text
一次释放三发追踪弹
```

也**不是**：

```text
一整片同时倾泻的弹幕
```

其实际射速、持续时间、目标选择、补充逻辑、冷却、火球伤害、同屏上限，
**以当前 `player_combat.gd`、`orbit_fireball.gd` 与 `ability_projectile.gd` 为真实依据**，
不要在设计文档里固化这些数值。

> **实现状态（2026-09-11 修正，2026-09-12 调整射速）**：本节描述的是**应有行为**。
> 第一次修正前 `cast_fireballs()` 只生成 3 个一经发射就不补位的投射物，
> 环绕数 3→0 衰减，屏幕上「总共只有三颗火球」——
> 与本节描述不符，属于实现缺陷，已修正为
> `orbit_fireball.gd`（常驻槽位）+ `ability_projectile.gd`（已发射的独立攻击弹）。
>
> 第二次修正：第一次修正把开火冷摆放回了**每个槽位内部**（0.18s），
> 三槽位同时倾泻 ≈ 16.7 发/秒，观感变成「一次性发射大量弹幕火球」。
> 现改为**全队共享一个开火节奏**（`FIREBALL_LAUNCH_INTERVAL`，每轮只射一颗，
> 由轮转到的槽位执行）。
>
> 不变量：技能激活期间 `orbiting_fireball_count() == 3` 恒成立；
> 每轮只射出**一颗**攻击火球；射速 = `1 / FIREBALL_LAUNCH_INTERVAL`，
> **不随环绕数量放大**。由 `tests/godot/fireball_skill_regression.gd` 断言。

### 9.3 忍术

- 大型向前移动的**螺旋丸式能量体**
- 能量通过**金币积累**
- **能量满后才能释放**，释放后**能量归零**
- 可飞越屏幕，其清理由**生命周期 / 最大移动距离 / 世界清理逻辑**负责

### 9.4 设计含义

| 能力 | 关卡设计解读 |
|---|---|
| 火球 | **持续型**武器技能，可持续清障，不是一次性爆发 |
| 忍术 | 需要攒能量的**周期性**大招 |
| 基础移动 | 跳 / 二段跳 / 滑铲 / 急降 / 贴绳 —— **不依赖技能**才是安全基线 |

**基线判断**：一条路线应当在**不使用任何技能**的前提下可通过，
技能只作为容错与风格化手段。

## 10. 验证要求

区分**自动验证**与**人工试玩**，二者不可互相替代。

### 10.1 自动验证负责

| 项目 | 手段 |
|---|---|
| 编译器校验 | `PatternCompiler.compile` / `validate` |
| 可达性（空间尺度） | `PREVIEW_SIZE` 与 `PlayerMotionProfile` 的跨度/高度比较 |
| **飞镖墙缺口是否需要操作** | 按站立 / 下蹲 / 单跳 / 二段跳四种姿态对照 `safe_gap_position`；缺口太低会「站着走过去」，属于失误 |
| **连续动作（动作句）** | 相邻障碍的**相遇时刻**间隔 ≤ 1.5 × `jump_time()` |
| **无意义空白** | `PatternCompiler` 的 `length` 由威胁结束时刻推导；设计工具统计尾段空白 |
| 节点引用 | 场景加载、`obstacle_scene != null` |
| Entry / Exit | 段场景标记存在性 |
| Pattern 重叠 | 坑重叠、安全口净高、出生范围 |
| Runtime Error | Godot headless 运行 |
| 生命周期 | 生成 / 回收 / `finish()` |
| 重开 | `R` 重开状态正确 |
| 暂停 | `P` / `Esc` 状态正确 |
| 回归测试 | `tests/godot/*.gd` |

运行方式：

```text
Godot --headless --path . --fixed-fps 60 --script tests/godot/<测试名>.gd
```

### 10.2 人工试玩负责

| 项目 |
|---|
| 手感 |
| 节奏 |
| 预警是否清楚 |
| 是否有压迫感 |
| 是否无聊 |
| Variation 是否容易辨认 |
| 难度变化是否自然 |
| **屏幕上是否还有大段只有平地** |
| **连续障碍之间是否真的读得出动作关系** |
| **飞镖墙看起来是否孤立** |
| **是否有明显的小高潮** |
| **Recovery 是否真的与高压内容形成对比** |

> **「可通过」与「有趣」是两个不同的验收目标。**
> 自动验证通过只说明前者。任何以「自动测试全绿」代替人工试玩的结论都不成立。

### 10.3 `needs_manual_playtest`

- **只有经过实际人工试玩后**，才根据项目规则更新该标记。
- 自动测试通过 ≠ 可以关闭该标记。
- 当前状态：**全部模板与 `Dart_Introduction` 仍为 `needs_manual_playtest = true`**。

## 11. 设计自检清单

提交任何关卡改动前，逐条确认：

- [ ] 每个新内容都显式标注了所属阶段（Introduce / Repeat / Vary / Escalate / Recovery）
- [ ] Introduce 只有单一机制，反应窗口 ≥ 0.45s（正式教学 ≥ 0.75s），前后有安全区
- [ ] Repeat 是同一机制出现 2~3 次，未引入新修饰
- [ ] Vary 只改变了**一个**主维度，且基础是已教过的 Pattern
- [ ] Escalate 只组合已教机制，存在明确可执行路径，无无解窗口
