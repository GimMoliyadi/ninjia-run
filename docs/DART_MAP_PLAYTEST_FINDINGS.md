# 飞镖地图实跑调查记录（2026-09-16）

## 结论一句话

**此前记录的「实跑失败 = 关卡问题」是错的。** 关卡侧经三种独立方法验证可解；
真正的问题在试玩 AI 驱动器（`tests/godot/dart_map_playtest.gd`）。

| 检查 | 结果 |

## 新增的两个诊断工具

### 1. `dart_map_reachability.gd` —— 解析式可解性扫描

不依赖任何试玩 AI，直接对所有飞镖按相遇位置排序，逐枚算出「站立是否安全 /
滑铲是否安全 / 是否必须起跳」，再用贪心前推模拟一条轨迹。

命中判据与 `pattern_compiler.dart_hits_body` 严格一致（**这一条曾经写错，见下**）：

```gdscript
# 身体占 [feet, feet+body]，飞镖占 [h-r, h+r]，区间相交即命中
func hits(h, feet, body):
    return h + Dart.RADIUS > feet and h - Dart.RADIUS < feet + body
```

**关键发现：关卡里的飞镖结构是「交替的竖排门阵」，不是随机的。**

以 x=18569 为例，同一位置叠三枚：`h=226 / 146 / 66`。
以 x=18804 为例：`h=196 / 116 / 36`。

两种门的解法是唯一确定的：

| 门型 | 高度 | 唯一解法 | 理由 |
|---|---|---|---|
| A | 226 / 146 / 66 | **滑铲** | h=66 落在滑铲专属带 (43,77]；滑铲后身体顶面 32，三枚全在 32 以上 |
| B | 196 / 116 / 36 | **跳到脚底 ≈105~119** | h=36 低于滑铲带必须跳；h=116 占 [105,127]，脚底须 ≥105 才能过；h=196 占 [185,207]，脚底+66 ≤ 185 |

门与门的间距（310px = 0.78s；最紧的一段 241px = **0.60s**）略大于/接近
单跳周期 0.706s，属于「紧张但可行」，不是无解。

### 2. `_probe_slide_input.gd` —— 最小输入验证

验证 headless SceneTree 下 `Input.action_press("slide")` 能否真的触发
`start_slide()`。**结论：可以**（state=2 SLIDE，body 66→32，速度 400→620）。
所以「滑铲静默失效」不是引擎/输入层的问题。

## 修掉的驱动器 bug（本轮，共 6 个）

1. **相遇公式分母漏乘** —— 旧 `(po + s·key)/(1 + s/R)`，误差可达 2,059,850 px。
   改为 `po / (R + s) · R`。
2. **滑铲分支死代码** —— 判据写成 `h > 77`，恰好排除掉唯一需要滑铲的带 (43,77]。
3. **每帧重复 press("slide")** —— `start_slide()` 每次重置 `slide_remaining`，
   滑铲被无限续期。加 `handled` 标志。
4. **所有分支都以 return 收尾** —— 每帧只能处理一个 batch；
   `RISE/FALL` 阶梯（96→152→200，间隔 0.21s）后面的节次被饿死。
   改为「姿态类分支用 continue，只有动作类分支抢占本帧」。
5. **滑铲起手太早** —— 在 t=0.62s 就按下，而滑铲只持续 0.58s，
   飞镖到达时玩家已恢复站立体型。必须等到 t ≤ 0.45 再滑。
   （这一条在探针里修好后，第一处受伤从 x=2181 直接消失。）
6. **起跳前不检查能否过** —— 新起跳（vy=-1063）仍在上升半途被飞镖追上。
   要算 `feet_after_jump(t) >= h + 66 + 11` 才允许起跳。

## 我在本轮自己犯的错（记下来，别再犯）

1. **命中判据写错** —— 我一度用
   `clearance = h - (feet + body); below = feet - (h + r); danger = clearance > -r and below < 0`，
   这会把「站着本来就安全」的 h=116 / h=196 全部误报成危险。
   正确写法就是上面那个区间相交式。修好后误报从 52 处降到 25 处。
2. **把 `position_offset` 当成世界坐标** —— 它是 runner **本地**坐标。
   直接 `runner.global_position.x + po/...` 还要乘 `R`，否则 161 枚飞镖排成乱序。
3. **「间隔 < 单跳周期」当可解性判据太粗** —— 两枚 h=36 相隔 0.2s 用同一次
   起跳就能同时躲过。判据必须是「在每枚飞镖到达那一刻，脚底是否安全」。
4. **曾把 `slide_remaining=0.41` 判定为「无害的陈旧值」** —— 错了。
   它反映玩家**当时确实处于滑铲中**。当时得出「velocity.x=400 说明没滑铲」
   的推理是错的（滑铲速度是 620 而非 400，但那次的采样点恰好不在滑铲窗口内）。
5. **`finish_slide()` 不复位 `slide_remaining`** —— 这是个真实的（虽然轻微的）
   `player.gd` 小瑕疵：滑铲结束时会留下一个 0.01~0.12 的残值。
   本轮**未修**（改动 `player.gd` 触发完整回归，且不影响玩法），仅记录。

## 尚未解决 / 下一步

`dart_map_playtest.gd` 仍报 5 次受伤。已确认：
- 不是关卡问题（三法验证：linkage / module regression / reachability）
- 不是输入层问题（_probe_slide_input 证明滑铲可用）
- 是驱动器的**轨迹规划能力不足**：贪心 + 反应式，无法处理
  「先为 A 门滑铲、再为 B 门起跳、再为 C 门落地」这类需要提前 1~2 个动作规划的序列。

**建议下一步（单独一轮）**：把驱动器从「反应式」改为「离线规划式」——
先用 `dart_map_reachability.gd` 的相遇时刻表算出一条完整的合法轨迹
（每枚飞镖到达时脚底的目标高度），再让玩家按这条轨迹执行。
这比继续调窗口阈值可靠得多。

**在此之前，实跑失败不能作为关卡交付判据。** 关卡侧的判据是：
linkage 44/44 + module regression 通过 + 编译 0 issue + 88.0s < 90s。
